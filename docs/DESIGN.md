# 设计说明

这份文档记录的是**为什么这样写**，而不是写了什么。代码本身能说明后者。

---

## 1. 问题的起点

属性测试的价值全在反例质量上。一个报出 40 元素失败数组的工具，和没跑过差不多；报出 `[1, 0]` 的工具，等于直接把 bug 指给你。

反例质量取决于收缩（shrinking）。而收缩能力取决于**生成器在生成时留下了多少信息**。

`moonbitlang/core/quickcheck` 的生成器签名是：

```
Generator[T] :: (Int32, RandomState) -> T
```

收缩靠独立的 `Shrink` trait，按类型给出候选：

```
trait Shrink { fn shrink(Self) -> Iter[Self] }
```

这对简单类型很好用，但它有一个结构性上限：收缩函数只能看到**最终的 T**。生成过程中做过的所有决策——长度是多少、走了哪个分支、`flat_map` 里选了哪个内层生成器——在 T 交给 `Shrink` 的那一刻就已经丢失了。

最典型的表现是依赖式生成（dependent generation）：

```moonbit
int_range(3, 9).flat_map(n => Gen::pure(()).array_with_size(n))
```

先生成 `n`，再生成长度恰为 `n` 的数组。收缩时按类型只能删元素或把元素改小，**改不了 `n`**。于是收缩要么停在原长度，要么产出一个长度不匹配、生成器根本不会产出的畸形值。

Hedgehog 把这个问题总结成一句话：*type-directed shrinking cannot shrink what the generator knew but the type forgot.*

---

## 2. 解法：让生成器返回收缩树

```
Gen[T] :: (Int, Rng) -> Tree[T]?
Tree[T] :: { value : T, kids : () -> Array[Tree[T]] }
```

生成的同时把收缩候选建出来。收缩不再是"猜"，而是"走一遍生成器自己铺好的路"。

`Gen::map` 保持树形；`Gen::zip_with` 让两侧分别收缩；`Gen::flat_map` 是关键：

```
flat_map(outer, f):
  跑 outer  → 得到 outer 树
  冻结内层随机流 inner_seed
  跑 f(outer.value) → 得到 inner 树
  合并树 = inner.value
           children = [对每个 outer 子节点: 重新跑 f(子节点值)]
                   ++ [inner 的子节点]
```

两条子节点列表的先后顺序是刻意的：**先收缩外层值**。外层值决定形状，形状先简化，随后的元素收缩才在正确的语境里进行。

因为 `f` 会被重新调用，内层生成器必须在同样的随机流下重跑，否则收缩出来的序列不可复现 —— 这就是 `inner_seed` 冻结的原因。

代价是：同一个 outer 值在收缩中可能被 `f` 调用多次。这是可接受的，因为内层生成器本身是纯的（随机流已冻结）。

---

## 3. 为什么子节点是 thunk

```
kids : () -> Array[Tree[T]]
```

收缩树的分支因子逐层相乘。`array_of` 生成一个 100 元素数组，每层就可能有上百个候选；三层下去就是百万级。

但搜索只走**一条**路径。提前展开等于为了一条路径付出整棵树的代价，2 秒的测试会变成挂死。

所以 `Tree` 的子节点必须是 thunk。`tree` 包里有一个专门的测试用计数器钉住这件事：

```moonbit
let built = [0]
let tree = Tree::lazy_node(10, fn() { built[0] = built[0] + 1; [...] })
assert_eq(built[0], 0)        // 构造时没跑
let children = tree.children()
assert_eq(built[0], 1)        // 问的时候才跑一次
assert_eq(children[0].children().length(), 0)
assert_eq(built[0], 1)        // 访问孙节点不会重跑父节点
```

没有这个测试，将来某次"顺手优化"很容易把惰性改掉，而症状是性能退化而非断言失败 —— 最难发现的那一类。

## 4. 为什么贪心，以及它保证了什么

`shrink` 的算法是深度优先 + 首次适配：

```
current = root
loop:
  for child in current.children():
    if 仍然失败(child.value):
      current = child; 记录索引; break
  else: 结束
```

它保证两件事：

1. **每一个报出的值都是生成器自己铺的路。** 收缩只沿已有的边移动，不会凭空造出生成器拒绝产出的值。这条保证了"反例是真的"。
2. **结果在直接子节点上已无更小者。** 也就是局部最小。

它**不**保证全局最小。全局最小需要在无限树（或至少是隐含无限的树）上做穷举，不可判定。Hedgehog、Hypothesis、QuickCheck 全部接受这个取舍，区别只在启发式。

顺带一提，`attempts` 和 `steps` 分开计数是有意的：一个被拒绝的候选消耗 attempts 但不消耗 steps。报告里这两个数字的比值能告诉你收缩路径有多"崎岖"——如果 attempts 远大于 steps，说明生成器产出了大量接近边界但不算失败的候选，通常是生成器本身值得调整的信号。

## 5. 拒绝（discard）为什么重要到要改类型

`run` 返回 `Tree[T]?` 而不是 `Tree[T]`，`None` 表示这次抽不出合法值。

不这么做的话，`filter` 只有两条烂路可走：返回一个不满足谓词的值（撒谎），或者抛异常（把控制流交给错误处理）。

引入 `None` 之后有三条规则：

1. 组合子里 `None` 向上传播（`map` / `zip_with` / `flat_map` / `array_of` 都要处理），所以一次失败的抽取会让整条管线跳过本 case，而不是产出一个半成品。
2. 跑器把 `None` 计为 discard，并受 `discard_limit` 约束。
3. **整轮一个有效样本都没有时，结果是 `GaveUp` 而不是 `Passed`。**

第 3 条是这批规则里最容易被忽略、后果最严重的一条。一个"所有 case 都被丢弃"的运行，如果报绿，就是最糟的答案：绿色的、而且毫无意义的。这条有专门的测试钉住。

也因为这个，`Outcome` 是三态而非二态。真实的测试工具需要"说不清"这个状态，假装不需要只会把它藏成 false negative。

## 6. 重放：存派生结果，不存配置

```
Replay :: { case_seed : UInt64, size : Int, path : Array[Int] }
```

`case_seed` 是这一 case 实际用的种子（由 base seed 派生），`size` 是它实际跑的大小，`path` 是收缩时走过的子节点索引。

不存 `base_seed` + `count`，因为一旦有人把 `count` 从 100 调到 500，`size` 调度就变了，同一个 case 号的种子还在但大小不同，重放会得到不同的值 —— 那就不叫重放了。

存派生结果之后，`replay` 与配置无关。代价是记录稍长，收益是别人改配置之后反例依然可复现。

`follow` 在路径越界时返回 `None` 而不是 panic：生成器改了之后旧路径自然可能失效，这时应该明说"这条路径现在不存在了"，而不是给一个当前代码产生不了的值。

## 7. 状态机：一次失败的抽象，和它教会我的事

第一版的想法很漂亮：命令用 `flat_map` 链式串起来，

```
build(state, n) =
  if n == 0 then pure([])
  else generate(state).flat_map(cmd =>
         build(apply(state, cmd), n-1).map(rest => cons(cmd, rest)))
```

`flat_map` 已经会"收缩外层值时重新派生内层"，那序列收缩岂不是白送？

跑出来是 `steps=0 over=0 candidates`。原因是：命令生成器是 `Gen::pure(Increment)`，本身就是叶子，没有子节点。`flat_map` 的子节点来自两处——外层树的子节点和内层树的子节点——而这条链上每一层的外层都是叶子，唯一的子节点只可能来自最深处的 `pure([])`，那也是叶子。**整棵序列树退化成叶子，一条命令也删不掉。**

这个失败很有价值，因为它精确地说明了 `flat_map` 能给什么、不能给什么：

> `flat_map` 提供的是**在既有元素上重新派生后缀**。它不提供**减少元素个数**。数组能收缩长度，是因为 `array_tree` 额外加了"砍半 / 砍最后一个"的结构候选；命令链没有这一层，所以不行。

修法是给序列单独建树。`draw` 负责依赖式生成（每步的合法性用 `precondition` 过滤），`sequence_tree` 负责在三类候选上展开：

1. **删除任意位置的一条命令**（每个下标一个子节点）
2. **砍掉后半段**
3. **原地简化某条命令**

第 1 条是关键。只删头的话，删掉第 k 条必须先删掉前面所有命令；而贪心搜索拒绝"删了就通过"的步骤，中间那条冗余命令就永远够不着——实测会卡在 5 条，删不到 3 条。

删除的安全性靠 `precondition`：被删命令导致后续命令失去前提时，`run_sequence` 跳过它而不是盲目执行。没有这一层，删命令会造出"失败但与原缺陷无关"的序列，那比不收缩更糟——它给了一个假的解释。

成本上说，每个节点生成 O(n) 个子节点、每个子节点重建 O(n) 的数组，单节点 O(n²)。命令数在十几条的量级，这不是问题；真要上百条，得换成增量式的表示。

## 8. 被放弃的设计

**惰性 memo 化的树。** 考虑过给 `kids` 加缓存避免重复求值。放弃了：贪心搜索每个节点的子节点只求一次，缓存不会命中，反而多一层开销和状态。

**全局最小化（如 Hypothesis 的 adaptive 策略）。** 需要记录完整生成轨迹并做重放式收缩，复杂度高一个量级。当前设计的局部最小已经能满足"把 20 条命令压成 1 条"的实际需求。

**让 `Outcome` 携带 `Error`。** 试过。属性代码会抛各种类型（`assert_eq` 的、自定义 `suberror`、库错误的），统一到 `Error` 后调用方拿到一个无法检视的类型；`raise?` 上下文里它甚至表现为 `Error?`，语义含糊。改成渲染好的 `String?` 之后，`Outcome` 不再有它用不上的类型参数，报告也更好读。

**覆盖率引导的模糊测试。** 有价值，但和属性测试是不同的技术栈（需要插桩或反馈通道），放进这个项目会稀释重点。留在路线图里。

## 9. 验证策略：拿它测自己

这个项目的核心主张是"验证能力"，所以它自己必须先通过自己的标准。

- **54 个测试，0 警告，0 未覆盖的公开 API。**
- **算法层对拍**：RNG 的混合函数对标 SplitMix 公布的 `mkSMGen 1337` 参考向量；`mix64(1)` 的期望值用 Python 独立实现算出来再写进断言，不是从自己的输出里抄的。
- **注入缺陷对照**：`examples` 里三个只改一行的 mutant，每个都断言**精确**的最小反例（`[1, 0]`、`[0]`、`" "`）。同时有对照组：换回正确实现，同一属性必须通过。
- **反向测试**：`filter` 谓词不可满足时必须 `GaveUp`；重放路径失效时必须返回 `None`；全 discard 的运行不能报 `Passed`。这些是"工具本身出错"的防线，比"工具报告失败"更容易被忽略。
- **性能红线**：树必须是惰性的，否则整个设计不成立。有计数器测试钉住。

一句话：如果这个库的收缩器退化了，它自己的测试会先红。
